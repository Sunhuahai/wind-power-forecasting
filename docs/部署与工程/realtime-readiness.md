# 实时预测准备（接入真实数据前）

更新：2026-11-15。当前状态：离线竞赛回放已完成（严格协议 9 节点，测试 RMSE 0.156009848）；实时预测尚未具备条件，本文记录差距、接口契约与分阶段计划。

## 一、现状与实时预测的差距

| 环节 | 现在（回放） | 实时预测需要 |
|---|---|---|
| NWP 入库 | 官方 CSV 批量导入，每小时一条，`issued_at` 为空 | 按批次到达，保留 `issued_at`、可多次修订；同一 `valid_at` 可能有多份预报 |
| 可用性假设 | 竞赛回放假设（起点可用未来 1–24 小时 NWP） | 真实到达时间：预测起点只能用**已到达**的批次 |
| 功率观测 | 批量导入历史 | 持续增量写入，迟到数据回填 |
| 模型 | 5 个基线模型（persistence/ridge/LGBM A/B/C） | **优化链（9 节点）没有推理入口**，需要打包成版本化 bundle |
| 推理 | `windpower forecast --origin` 跑基线 | 按起点调度、幂等、失败可重试、写预测与溯源 |
| 监控 | 无 | 滚动 RMSE/MAE、覆盖率、延迟、漂移告警 |
| 站点元数据 | 归一化功率 0–1 | 需要额定容量（MW）换算，以及时区/时钟定义 |

## 二、接口契约（建议）

### 1. NWP 批次入库

```
nwp_revisions(farm_id, issued_at, valid_at, u10, v10, u100, v100, received_at, source, quality)
主键 (farm_id, issued_at, valid_at)
```

- `issued_at`：预报发布时刻（业务时钟）。
- `received_at`：实际落库时刻，用于审计迟到。
- 预测起点 `origin` 取数规则：**只用 `received_at <= origin` 且 `issued_at <= origin` 的批次，取最新一份**；缺失即报错，不静默回退。

### 2. 功率观测

沿用 `power_observations`，增加 `received_at`；预测时只读 `observed_at < origin` 的观测（现有 `history_strictly_before_origin` 已是这个语义）。

### 3. 模型 bundle

一个目录一个版本，例如 `models/wind_v1/`：

```
manifest.json        # 版本、创建时间、组成树、各组件特征列、权重、训练数据口径、文件校验和
components/<id>.joblib
```

manifest 里用表达式树描述组合关系（见 `src/windpower/serving/compose.py`）：

```json
{"op": "add",
 "terms": [{"coef": 0.725116, "node": {"op": "add", "terms": [ ... ]}},
           {"coef": 0.274884, "node": {"op": "component", "id": "mlp"}}]}
```

好处：组合关系是**数据**而不是代码，换权重/换分支不用改推理代码，也便于回溯某次预测用的到底是哪套权重。

### 4. 推理入口

```
python -m windpower.serving.predict --origin 2026-11-16T00:00:00 --bundle models/wind_v1 --dry-run
```

- 幂等：同一 `(bundle_version, origin, farm)` 重复运行只覆盖同一行。
- 输出：24 小时预测 + 每个组件的贡献（可解释性）+ 数据来源（NWP 批次 id、观测截止时刻）。
- 失败语义：NWP 不完整 / 历史功率缺口 / 特征 NaN → **该站点该起点跳过并告警**，不产出猜测值。

## 四、需要你提供的信息（P1 的前置）

> 下面 6 条是启动 P1 的最小信息集；不确定的可以先按"每日 00:00 出一次、单模式、无修订"的默认假设，我在代码里留成可配置项。

1. **NWP 来源与格式**：文件落地 / API？字段名、时间分辨率、提前量范围、是否有多个模式（多批次）。
2. **发布与到达时间**：`issued_at` 与 `received_at` 是否可区分；迟到数据的处理规则。
3. **观测来源**：功率/风速的采集频率、单位、是否有额定容量（MW）、迟到与补数规则。
4. **站点元数据**：十站的额定容量、时区（是否统一）、是否同一时钟。
5. **调度与 SLA**：每天几点出预报、允许延迟多久、失败是否需要人工介入。
6. **存储与运行环境**：是否沿用本机 PostgreSQL 18.7，还是要上容器/云。

## 五、已知风险

1. **分布漂移**：模型全部在 2012 数据上训练，真实数据接入后季节、机组、限电行为都可能不同；上线前必须用一段真实历史做**影子回放**，并设定再训练触发条件。
2. **NWP 批次不一致**：真实业务里预报会被修订，训练时用的是"唯一一份"，推理时若用修订后版本，特征分布会变；需要固定取数规则并记录版本。
3. **限电/弃风**：训练数据里没有限电标记，真实生产数据里大量低功率是人为限电而非风小，直接套用会系统性高估。**这是上线前最大的风险**，强烈建议先补限电标记。
4. **时钟与时区**：本项目数据是无时区源时钟，接入真实数据时必须显式定义时区与夏令时处理。
