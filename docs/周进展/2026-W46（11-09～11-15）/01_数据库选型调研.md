## 一页摘要

| 问题 | 结论 |
|---|---|
| 选哪一类 | 通用关系型为主干（业务数据、实验、回滚），时序能力作为同一库内的扩展 |
| 选哪个产品 | **PostgreSQL 18.6 + TimescaleDB 2.32.x** |
| 为什么不是“另一个库” | TimescaleDB 是 PostgreSQL 扩展，事务、外键、JSONB、备份、HA、ORM 全部沿用；不存在“换库”这一步 |
| 为什么不换 MySQL | 能力够但需要重写数据访问层；分区表不支持外键、唯一索引须含分区键；没有时序能力平滑演进路线 |
| 为什么不用 ClickHouse / InfluxDB | 弱事务、异步去重/不可变文件，与“频繁幂等订正 + 关系追溯”冲突；适合当分析副库或遥测库 |
| 为什么不选 DuckDB 当主库 | 单进程写入、乐观并发，不能做在线服务；但它是离线分析与特征探索的好工具 |
| 实测收益 | 列存+压缩代理测量：NWP 表 −91.8%、预测表 −95.0%、功率表 −93.0%（约一个量级） |
| 主要代价 | ① 扩展与主库小版本耦合（2.32.0 只支持到 PG 18.6，升级须先升扩展）② TSL 许可证下不能把数据库能力作为服务对外售卖 |
| 当前动作 | 备而不发：迁移草案写好、不注册为 Alembic 版本；真实数据到位、满足三条启动条件再执行 |

累计判断链只有一句：**我们的负载是“强关系约束下的中等规模时序处理 + 频繁幂等订正”，能同时满足这两条且不制造迁移债的，只有“关系库 + 时序扩展”这一格。**

## 第一章　数据库类型全景

### 1.1 分类先于产品对比的原因

选型最常见的错误是“拿产品比产品”：把 ClickHouse 和 PostgreSQL 放在一张表里比 QPS，得出“ClickHouse 快 100 倍”的结论，再用它去解释为什么不适合当业务库——这类比较本身没有信息量，因为两者的**物理布局与一致性模型不同**，擅长的负载根本不在同一坐标系。

所以先按三个维度分类，再看每一类能承担什么：

| 维度 | 取值 | 决定什么 |
|---|---|---|
| 存储布局 | 行存 / 列存 / LSM 树 / 混合（热行存+冷列存） | 单条读写与批量扫描谁更快 |
| 数据模型 | 关系 / 宽表 / 文档 / 键值 / 指标 | 关系与约束能不能表达 |
| 部署形态 | 共享服务 / 嵌入式 / 无服务（文件） | 能不能多进程并发、能不能在线服务 |

### 1.2 六类形态

#### 1.2.1 通用关系型数据库（行存 OLTP）

**代表**：PostgreSQL、MySQL/InnoDB、SQLite（嵌入式变体）。

**机制**：数据按行连续存放；B-Tree 索引指向行；MVCC 提供读写不阻塞；WAL 保证崩溃恢复；事务、外键、CHECK 约束在引擎层强制。

**优势**：单条写入与点查极快；关系与约束能表达业务规则；`UPSERT`（`ON CONFLICT`）天然支持幂等覆盖；生态成熟（备份、复制、监控、ORM、迁移工具）。

**边界**：跨年大范围聚合要扫整行，I/O 放大；高频 `UPDATE` 产生死元组，依赖 autovacuum；没有开箱即用的按时间分块与冷数据压缩。

**在本项目的位置**：主库。业务数据（场站、实验、预测、观测）都在这一层。

#### 1.2.2 时序数据库（TSDB）

**代表**：TimescaleDB（PG 扩展）、InfluxDB、QuestDB、TDengine。

**机制**：按时间分区（或 LSM 分片），时间戳即主键维度；写入路径优化为追加；按时间范围裁剪；配套保留策略与降采样。

**优势**：写入吞吐高；按时间窗查询快；历史数据按块删除与压缩；天然支持“降采样视图”。

**边界**：通用 SQL 能力参差；更新与删除语义弱（InfluxDB 3 底层是不可变 Parquet 文件）；关系与约束通常缺失或受限；迁移到它们的代价等于换一整套工具链。

**关键区分**：TimescaleDB 与其余产品不同——它是 PostgreSQL 的扩展，**继承了关系型的全部能力**。把它和 InfluxDB 并列会得出错误结论（第九章会展开）。

**在本项目的位置**：作为同一主库内的增强层，而不是独立系统。

#### 1.2.3 列式分析型（OLAP）

**代表**：ClickHouse、DuckDB、StarRocks、Doris。

**机制**：按列存储，同列值连续；向量化执行 + 高压缩；大范围扫描只读需要的列。

**优势**：亿级行聚合常在一秒内；压缩比高；适合报表、看板、批量特征统计。

**边界**：事务弱（ClickHouse 多语句事务仍标注实验性）；`ReplacingMergeTree` 只在后台合并时去重，合并前查询会读到重复行，需要 `FINAL` 牺牲性能；无标准外键；小批量点查容易导致 CPU 饱和；DuckDB 是单进程模型，不适合共享服务。

**在本项目的位置**：未来的分析副库、离线分析工具。**不是主库**。

#### 1.2.4 嵌入式 / 单文件

**代表**：SQLite、DuckDB（嵌入模式）。

**机制**：库即文件，进程内直接读写，没有网络协议层。

**优势**：零运维；单机工具、边缘设备、离线分析极方便；SQLite 开 WAL 后支持一写多读。

**边界**：SQLite 是**库级写锁**，同一时刻只允许一个写事务，多进程并发回写会触发 `SQLITE_BUSY`；没有细粒度权限、没有流复制；不适合“采集进程 + 推理进程 + API”同时写的服务形态。

**在本项目的位置**：本地工具、缓存、单机分析；生产服务不用。

#### 1.2.5 文档型与键值型

**代表**：MongoDB、Redis。

**机制**：MongoDB 存 BSON 文档，schema 自由；Redis 内存数据结构，毫秒级。

**优势**：MongoDB 适合以文档为单位、字段高度动态的数据；Redis 适合缓存最新预测、会话与短期状态。

**边界**：MongoDB 的时序集合对唯一索引与更新有限制，且我们的数据是强结构化的，文档模型反而浪费存储（字段名重复）；Redis 内存昂贵，缺少多维时间范围检索与关联统计。

**在本项目的位置**：MongoDB 无必要；Redis 仅在接口 QPS 上来后做前置缓存。

#### 1.2.6 列式文件格式（非数据库）

**代表**：Parquet、ORC。

**机制**：静态列式文件，带统计信息（min/max），支持谓词下推与字典编码。

**优势**：与 Pandas/Polars/Arrow 零拷贝互通；压缩比高；跨工具通用；适合数据快照与训练样本归档。

**边界**：无事务、无约束、无并发控制、无服务——它不是数据库。

**在本项目的位置**：检查导出、训练样本快照、跨环境交换。

### 1.3 把类型映射到“能不能当主库”

| 形态 | 能当业务主库？ | 原因 |
|---|---|---|
| 通用关系型 | 能 | 事务、关系、约束、幂等写入齐备 |
| 时序库（扩展形态） | 能（TimescaleDB） | 本质是关系库 + 时序层 |
| 时序库（独立产品） | 通常不能 | 关系与事务能力不足以承担业务表 |
| 列式 OLAP | 不能 | 弱事务、无外键、点查弱 |
| 嵌入式 | 不能（多进程服务） | 写并发模型不支持 |
| 文档/KV | 不建议 | 关系表达与约束能力不足 |
| 文件格式 | 不能 | 无服务、无事务 |

一句话：**类型只决定“擅长什么负载”，不决定“能不能做业务库”；能同时做业务库与时序处理的，只有“关系库 + 时序扩展”这一格。**

## 第二章　需求画像

### 2.1 数据流与角色

系统里有四类数据，流向不同：

```
NWP 预报（多批次、可修订） ─┐
                          ├─→ 特征构造 ─→ 模型（树/MLP 组合） ─→ 预测结果 ─→ 考核与看板
功率观测（可迟报、可补录） ─┘                     ↑
                                          实验记录（模型版本、参数、指标）
场站元数据（容量、坐标、时区）──────────────┘
```

四类数据的读写特征完全不同：

| 数据 | 写频率 | 读模式 | 更新模式 |
|---|---|---|---|
| NWP 预报 | 每天若干批（每批覆盖 72 小时） | 按起点+目标时刻取窗口 | 迟到/修订会覆盖历史批次 |
| 功率观测 | 每小时或 15 分钟 | 按场站取 24 小时历史 | 迟报与补录 |
| 预测结果 | 每次运行 × 24 小时 × 场站数 | 按运行/按目标时刻取 | 重跑订正 |
| 实验记录 | 每次实验一条 | 按时间与模型取 | 基本只追加 |

### 2.2 七条硬需求与技术约束

| 需求 | 具体场景 | 转化成的技术约束 | 满足不了的后果 |
|---|---|---|---|
| 关系与完整性 | 功率属场站、预测属实验、实验关联模型 | 主外键、NOT NULL、CHECK | 孤儿数据、口径混乱 |
| 幂等写入 | 重复导入、任务重试、预测重跑 | 唯一键 + `ON CONFLICT DO UPDATE` | 重复行，指标统计虚高 |
| 时间窗查询 | 取某站某段时间的历史与预报 | 时间索引 + 分区裁剪 | 大表全扫，延迟不可控 |
| 历史回放 | 还原“那一刻真实可用的预报” | 发布/到达/有效三种时间分别落库 | 回测穿越，结论不可信 |
| 实验追溯 | 每条预测追到模型、参数、数据版本 | 实验表 + 输入版本标识 + 权重文件哈希 | 无法复现，无法审计 |
| 历史清理 | 按年限保留、按期归档 | 按块删除（不产生死元组） | 表膨胀、VACUUM 追不上 |
| 在线服务 | 每日出预报、看板查询、失败可查 | 并发连接、备份、PITR、告警 | 数据库不可用即导致服务中断 |

### 2.3 数据量与增长曲线

当前实测（2026-11-16，`pg_stat_user_tables`）：

| 表 | 行数 | 堆大小 | 索引大小 | 合计 |
|---|---:|---:|---:|---:|
| `nwp_forecasts` | 175,440 | 49 MB | 7.4 MB | 56 MB |
| `predictions` | 127,296 | 13 MB | 17 MB | 30 MB |
| `power_observations` | 175,440 | 13 MB | 7.4 MB | 20 MB |
| 其他（实验、场站、迁移） | 41 | <1 MB | <1 MB | <1 MB |
| **整库** | — | — | — | **约 115 MB** |

注意一个反直觉现象：**`predictions` 的索引（17 MB）比数据本身（13 MB）还大**。原因是它有三个 B-Tree（主键 + 时间 + 实验外键），而列存可以把这类二级索引开销整体消掉——这是第六章收益的主要来源之一。

增长测算（逐年）：

| 场景 | 算式 | 每年行数 | 量级 |
|---|---|---:|---|
| 现状：10 站，每小时 | 10 × 8,760 | 87,600 | 十万级 |
| 50 站，15 分钟功率观测 | 50 × 96 × 365 | 1,752,000 | 百万级 |
| 50 站，NWP 每天 4 批 × 72 提前量 | 50 × 4 × 72 × 365 | 5,256,000 | 百万级（最大） |
| 50 站，每天 8 次预测 × 24 小时 | 50 × 8 × 24 × 365 | 3,504,000 | 百万级 |
| 100 站，15 分钟功率观测 | 100 × 96 × 365 | 3,504,000 | 百万级 |
| 机组级遥测：2000 台 × 15 分钟（仅对照） | 2000 × 96 × 365 | 70,080,000 | 千万级 |

三点判断：

1. **行数最多的通常是 NWP**（50 站口径下是功率观测的 3 倍），因为每条预报要覆盖 72 个提前量、每天还要发多批。
2. **预测明细紧随其后**，随“模型版本数 × 每日运行次数”线性增长。
3. 机组级遥测会跳到千万级，但属于设备监控域，不在功率预测主链路内；若后续纳入该域，再评估专用时序方案。

结论：**需要“按时间查、按时间删、按时间压”的核心大表是 NWP（`nwp_forecasts`、`nwp_revisions`）与预测明细（`predictions`），而不是功率观测（`power_observations`）。** 前三张表构成列存压缩的主要收益对象；`power_observations` 也会转为超表（30 天 chunk，详见 8.5 节），但因单站年增量小暂不急于压缩。

### 2.4 写读模式与并发

| 维度 | 现状 | 生产预期 | 对库的要求 |
|---|---|---|---|
| 写入 | 批量导入 + 每日回写 | 每天几百到几万行，峰值在整点后 | 批量写入效率、幂等键 |
| 读 | 训练取数（全量）、报表（聚合） | 训练取数 + 看板 + 接口点查 | 时间裁剪、并行扫描 |
| 并发 | 单进程 | 采集 + 推理 + API + 报表 | 多连接、连接池、读写分离 |
| 事务 | 单表批量 | 多表（实验+预测）原子写 | 事务边界清晰 |

### 2.5 时间语义：五条时间轴不能混

这是风电预测最容易被忽略、也最容易造成“回测作弊”的地方：

| 时间 | 含义 | 谁产生 | 用途 |
|---|---|---|---|
| `issued_at` | 预报起报时刻（模式起算时间） | 气象源 | 判断预报批次 |
| `received_at` | 实际到达本系统的时刻 | 我们的采集端 | **回放时只能用 `received_at ≤ 评估时刻` 的批次** |
| `valid_at` | 预报目标有效时刻 | 气象源 | 与功率对齐 |
| `observed_at` | 观测采样时刻 | 场站/表计 | 标签 |
| `origin` | 预测起点（我们发起预测的时刻） | 我们的调度 | 组织 24 小时预测块 |

五条时间混用会直接导致两类错误：**回测穿越**（用了未来才到的预报）与**时区错位**（把 UTC 预报当本地时间用）。

### 2.6 非功能需求

| 项 | 目标 | 依据 |
|---|---|---|
| RPO | ≤ 5 分钟 | 允许重算一次预报，不接受丢一天数据 |
| RTO | ≤ 1 分钟（自动切换）/ ≤ 1 小时（恢复演练） | 每日出预报有固定时间窗 |
| 备份 | 每日全量 + WAL 归档，保留 14–30 天 | 支持 PITR |
| 可用性 | 单库 99.9%（月度） | 内部系统，不需多地多活 |
| 合规 | 数据自持、遥测可关 | 生产环境不出内网 |

### 2.7 由需求推出候选范围

把 2.2 的七条要求逐条对照 1.3 的表：

- 关系 + 事务 + 幂等 → 只剩关系型；
- 时序增长 + 按块删除 + 冷数据压缩 → 关系型里只有带时序扩展的能满足；
- 在线服务 + 备份 + HA → 排除嵌入式；
- 历史回放 + 实验追溯 → 需要强 schema 与约束，排除文档型；
- 分析副库 → 可选列存，但不承担主链路。

**候选收敛为 4 个**：PostgreSQL（裸）、PostgreSQL + TimescaleDB、MySQL、SQLite（备选/工具位）。其余 6 个作为“特定任务”保留在评估表里，用于说明“为什么不是它”。

## 第三章　候选逐个深评

每个候选按同一模板写：**定位 → 机制 → 优势 → 边界 → 在本项目的裁决 → 如果选它会发生什么**。这样比较的是“总代价”，不是单项指标。

### 3.1 PostgreSQL（裸）

**定位**：通用关系型数据库的事实标准。

**机制**：
- 行存堆表 + B-Tree / BRIN / GIN / GiST 索引；
- MVCC：读写互不阻塞，旧版本留在堆里等 VACUUM；
- WAL：先写日志再落盘，支持崩溃恢复、流复制、PITR；
- 声明式分区（`PARTITION BY RANGE`），分区裁剪在规划期完成；
- `INSERT ... ON CONFLICT DO UPDATE` 原子幂等；
- JSONB 支持 GIN 倒排索引，可对半结构化字段做等值与包含查询。

**优势**：
1. 事务、外键、CHECK 一步到位，业务规则不用搬到应用层；
2. 幂等写入一条 SQL 解决；
3. 备份/HA/监控/ORM/迁移工具最成熟，团队学习成本最低；
4. 扩展生态强（PostGIS、pgvector、pg_cron 等），未来要加能力有路可走。

**边界**：
1. 高频 `UPDATE` 产生死元组，需要 autovacuum 调优；
2. 纯行存，跨年大范围单列聚合 I/O 放大明显；
3. 没有自动分块与冷数据压缩——要自己引 pg_partman、自己写归档脚本；
4. 分区数一多，规划时间上升，`DETACH PARTITION` 要自己编排。

**在本项目的裁决**：**合格且稳妥**，是“不带任何扩展”的基线形态。当前 115 MB 规模完全够用。问题不在能力，而在三年后的增长：NWP 与预测明细会成为“需要按时间删、需要压缩”的表，那时要么手工维护分区与归档脚本，要么做一次迁移。

**如果选它会怎样**：短期零成本；中期需要自建“分区管理 + 历史归档 + 报表预聚合”三套脚本（每套都要监控与排障）；长期若数据涨到需要列存压缩，仍要迁移到扩展形态。

### 3.2 PostgreSQL + TimescaleDB

**定位**：PostgreSQL 的时序扩展，保持同一套内核。

**机制**（详见第五章）：
- hypertable：按时间自动切 chunk，查询期裁剪；
- hypercore：冷 chunk 转列存，按类型选编码；
- continuous aggregate：增量刷新 + 实时合并；
- policy/job：保留、压缩、刷新由后台 worker 执行，有运行历史；
- 时序函数：`time_bucket`、`time_bucket_gapfill`、`locf`、`time_weight`。

**优势**：
1. **不换库**：事务、外键、JSONB、备份、HA、ORM、Alembic 全部沿用；
2. 自动分块省掉分区运维；
3. 列存压缩把存储与备份降一个量级（第六章实测）；
4. 保留策略用 `DROP CHUNK`，删除瞬时且不膨胀；
5. 报表走连续聚合，不用每次扫原始表。

**边界**：
1. 唯一索引必须包含分区列；
2. 不支持把行更新到另一个 chunk（含改分区列的 upsert）；
3. hypertable 之间不能建外键；
4. 压缩块上零散 `UPDATE`/`DELETE` 代价高，大改要先转回行存；
5. 扩展版本与 PG 小版本耦合，升级顺序固定；
6. TSL 许可限制“对外提供数据库服务”。

**在本项目的裁决**：**生产主库**。四条硬限制我们全部满足（四张表主键都含时间列，外键都指向普通表，写入不修改时间列）。

**如果选它会怎样**：与 3.1 相比，应用代码零改动，运维多一个扩展版本要跟；收益是存储、删除、报表三条路径同时变简单。

### 3.3 MySQL / InnoDB

**定位**：另一个通用关系型数据库，互联网运维经验最普及。

**机制**：
- 聚簇索引：数据即主键 B-Tree 的叶子，主键范围扫描极快；
- undo log + 就地更新，表空间膨胀通常小于 PG；
- 分区表（`PARTITION BY RANGE`），但**分区表不支持外键**，且唯一索引必须包含分区键；
- 无 BRIN 索引；无列存；物化视图只有全量 `REFRESH`。

**优势**：主从复制成熟；团队熟悉；点查性能好。

**边界**：
1. **分区 + 外键不可兼得**——我们恰恰既要按时间分区，又要外键约束；
2. 没有 BRIN，时序数据的二级索引体积压不下来；
3. 复杂 Join / CTE / 窗口函数的优化器能力弱于 PG；
4. 没有“时序能力平滑演进”的路线（没有官方时序扩展生态）。

**在本项目的裁决**：**合格备选，但没有迁移理由**。能力上能承担，代价是把数据访问层、迁移脚本、验收脚本全部重写一遍。

**如果选它会怎样**：一次性重写成本 + 永久失去“分区表带外键”这一组合；未来要时序能力只能换库或外挂系统。

### 3.4 SQLite

**定位**：嵌入式关系库，单文件。

**机制**：B-Tree 页式存储；WAL 模式下支持一写多读；无网络协议层，进程内调用。

**优势**：零运维、单文件可拷贝、适合本地工具与边缘设备。

**边界**：
1. **库级写锁**：同一时刻只有一个写事务，多进程并发回写会报 `SQLITE_BUSY`；
2. 无细粒度权限、无流复制、无在线备份（有 backup API 但要自己写）；
3. 无并行查询、无分区。

**在本项目的裁决**：**单机工具位**。可以作为本地缓存或离线分析的小库，不能承担“采集 + 推理 + API”同时写的服务形态。

### 3.5 ClickHouse

**定位**：列式分析数据库，海量扫描聚合的标杆。

**机制**：
- MergeTree 家族：按分区键与排序键组织数据，写入即产生不可变小文件，后台 merge；
- 向量化执行 + SIMD，聚合吞吐极高；
- 高压缩比（ZSTD/LZ4）；
- `ReplacingMergeTree` 做“去重”，但**只在 merge 时异步去重**，merge 前查询会读到重复行，除非加 `FINAL`（性能代价大）。

**优势**：亿级行聚合秒级返回；适合看板、误差明细统计、日志分析。

**边界**：
1. 事务弱：多语句事务仍标注实验性；
2. 无标准外键；
3. 幂等覆盖不是设计目标——我们的“重跑订正”会变成“写两份，查询时再去重”；
4. 小批量点查（高 QPS）容易导致 CPU 饱和；
5. 与 PG 的生态隔离：ORM、迁移、备份都要换。

**在本项目的裁决**：**远期分析副库**。当误差明细到十亿行、需要秒级多维聚合时再引入，用同步管道把结果推过去。

### 3.6 DuckDB

**定位**：进程内列式分析引擎。

**机制**：向量化执行；直读 Parquet/CSV；与 Arrow 内存格式零拷贝；MVCC + 乐观并发（写冲突报错）。

**优势**：无需部署；对 Parquet 做 SQL 分析极快；与 Polars/Pandas 互操作顺滑。

**边界**：
1. 单进程模型，多进程共享写入要靠 Quack 或 DuckLake（PostgreSQL 做 catalog）；
2. 不适合 7×24 在线服务；
3. 无细粒度权限与复制。

**在本项目的裁决**：**离线分析工具**。适合“把导出的 Parquet 拿来做特征探索与误差下钻”，也可以作为冷数据的查询层。

### 3.7 InfluxDB 3

**定位**：为设备遥测与指标设计的时序库。

**机制**：Rust + Arrow + Parquet 架构；列式存储；按时间分片；SQL 与基础 JOIN。

**优势**：高基数指标写入吞吐高；自带保留策略与降采样。

**边界**：
1. 无完整 ACID 与外键；
2. 底层是**不可变 Parquet 文件**，历史点的幂等覆盖（订正）不是设计目标；
3. 开源版在历史跨度与集群能力上有限制；
4. 关系管理能力弱，“场站—实验—预测”的拓扑表达不了。

**在本项目的裁决**：**不选**。它擅长的是 PLC/SCADA 秒级遥测，不是“带关系与订正的预测链路”。

### 3.8 MongoDB

**定位**：文档数据库。

**机制**：BSON 文档；无固定 schema；副本集；时序集合（Time Series Collection）。

**优势**：字段高度动态时方便；开发迭代快。

**边界**：
1. 时序集合对唯一索引与更新操作有限制；
2. 我们的数据是强结构化的，文档模型会重复存储字段名，反而浪费；
3. 跨表关联能力弱，追溯查询要靠应用层拼装。

**在本项目的裁决**：**不选**。没有需要它的场景。

### 3.9 Redis

**定位**：内存数据结构服务。

**机制**：单线程执行命令；RDB/AOF 持久化；丰富数据结构与过期策略。

**优势**：亚毫秒级；适合缓存最新预测、限流、会话。

**边界**：内存昂贵；无多维时间范围检索与关联统计；持久化不是为长期数据设计的。

**在本项目的裁决**：**未来的前置缓存**。当调度中心高频轮询“最新一版预测”时引入，不做主存。

### 3.10 Parquet（文件格式，非数据库）

**定位**：列式文件格式。

**机制**：列存 + 字典/RLE 编码 + 行组统计（min/max），支持谓词下推。

**优势**：跨工具通用；压缩比高；训练样本快照的标准载体。

**边界**：无事务、无约束、无并发、无服务。

**在本项目的裁决**：**数据交换与快照**。用于导出检查、跨环境传输、离线训练样本冻结。

### 3.11 候选对比总表

| 候选 | 一句话定位 | 能不能当主库 | 在本项目的角色 |
|---|---|---|---|
| PostgreSQL | 通用关系型基线 | 能 | 基线形态 / 对照 |
| **PostgreSQL + TimescaleDB** | 关系 + 时序 | 能 | **生产主库** |
| MySQL | 通用关系型备选 | 能 | 合格备选 |
| SQLite | 嵌入式关系型 | 不能（多进程） | 本地工具 |
| ClickHouse | 列式分析 | 不能 | 远期分析副库 |
| DuckDB | 进程内分析 | 不能 | 离线分析 |
| InfluxDB 3 | 遥测时序库 | 不能 | 不选 |
| MongoDB | 文档库 | 不建议 | 不选 |
| Redis | 内存缓存 | 不能 | 未来缓存 |
| Parquet | 列式文件 | 不能 | 交换与快照 |

## 第四章　评分体系

### 4.1 为什么要有两套权重

同一组能力，换一个前提，排序就会变化：

- **实验假设口径**：前提为“115 MB、10 个站、本地单机实验”。此时“运维复杂度”和“迁移成本”权重很高，结论是 PostgreSQL（89）> TimescaleDB（84）。
- **生产环境口径**：前提为“面向 Linux 服务器生产环境，多年、多站、在线服务、可扩容”。此时“时序能力”从可选项变成决定三年后是否需要停机重构的关键维度，“运维复杂度”相对降权——因为 TimescaleDB 与 PostgreSQL 共用同一套运维工具链。

两套口径的评分均予以保留，用于不同阶段假设下的敏感性对照。

### 4.2 维度与打分锚点

1–5 分的锚点预先定义如下，避免主观打分：

| 分 | 含义 |
|---|---|
| 5 | 开箱即用，无需额外工程 |
| 4 | 原生支持，需要少量配置 |
| 3 | 需要额外组件或脚本，但成熟 |
| 2 | 需要自研或受限使用 |
| 1 | 基本不具备 |

八个维度：

| 维度 | 考察什么 | 为什么重要 |
|---|---|---|
| 关系与完整性 | 主外键、约束、事务 | 业务数据不能有孤儿与口径漂移 |
| 幂等写入 | 唯一键 + 冲突更新 | 重试与重跑是常态 |
| 时序能力 | 分块、裁剪、压缩、保留 | 决定三年后的存储与删除成本 |
| 分析聚合 | 窗口函数、物化视图、向量化 | 误差报表与看板 |
| 实时写入 | 并发连接、批量写 | 采集与推理同时跑 |
| 实验追溯 | 强 schema、元数据、版本标识 | 结论可复现 |
| 迁移与生态 | 驱动、ORM、迁移工具、备份、HA | 换库等于换一整套工具 |
| 运维复杂度 | 部署、升级、监控、排障（越高越简单） | 团队规模有限 |

### 4.5 敏感性：权重调整对结论的影响

分数是权重的函数，需要明确结论在何种权重假设下会发生变化。以下为三次反向敏感性检验：

1. **把时序能力降回 15、运维复杂度升到 12**：TimescaleDB 88.2，PG 84.6——仍然领先，但差距从 10.4 分缩到 3.6 分。
2. **把迁移与生态升到 16、时序能力降到 18**：TimescaleDB 91.4，PG 85.0——领先幅度反而扩大，因为 TimescaleDB 的迁移成本本身就是“继承 PG”。
3. **只保留关系、事务、迁移、运维四项（等于回到“能不能用”）**：TimescaleDB 与 PG 并列——这正是关键结论：**两者的差异不在“能不能用”，只在“三年后要不要迁移”。**

### 4.6 评分结果的解读边界

- 分数反映给定权重下的工程综合适配度，而非性能排名；
- 差 10 分不等于差 10 倍；
- 真正的取舍只有两条：**版本耦合**与**许可证**（第七章）；
- 任何“某库比某库快 N 倍”的说法，若没有明确负载与硬件，都不该进入选型结论。

## 第五章　为什么是 TimescaleDB：机制级拆解

本章聚焦于 TimescaleDB 核心能力的底层机制与工程代价，不重复第四章的评分细节。

### 5.1 自动时间分块（hypertable / chunk）

**工作机制**：

1. 建表时声明一个时间维度（如 `valid_at`），`create_hypertable()` 把表登记为超表；
2. 超表在物理上由若干 chunk（子表）组成，每个 chunk 覆盖一个时间区间（默认 7 天）；
3. 新数据到来时，后台自动创建下一个 chunk，无需人工预建分区；
4. 查询带时间条件时，规划器按 chunk 的时间范围做**裁剪**，只扫描命中的 chunk；
5. 每个 chunk 有自己的索引（更小、更可能常驻内存）。

**与原生分区的关系**：

| 能力 | 原生 PG 分区 | hypertable |
|---|---|---|
| 创建分区 | 手工预建或 pg_partman | 自动 |
| 裁剪 | 支持 | 支持 |
| 分区数管理 | 自己控制，过多影响规划 | 按 chunk 间隔自动滚动 |
| 删除历史 | `DETACH + DROP` | `DROP CHUNK`（策略化） |
| 冷数据压缩 | 无 | hypercore |
| 跨分区更新 | 支持（同分区内） | 不支持跨 chunk 移动行 |

**定容口径（官方）**：让“正在写入的 chunk 的索引”占内存不超过 25%；默认 chunk 间隔 7 天。举例：索引每天增长 2 GB，64 GB 内存的机器适合 1 周 chunk；每天 10 GB 则用 1 天。

**代价**：
- 间隔太小 → chunk 数量爆炸，规划与元数据开销上升；
- 间隔太大 → 裁剪粒度粗，删除不灵活，压缩块也更大；
- 时间列不能为 NULL；唯一索引必须包含时间列。

### 5.2 列存与压缩（hypercore）

**工作机制**：

1. chunk 到达设定年龄（如 90 天）后，后台作业把它从**行存**转成**列存**；
2. 转换时把多行同列的值打包成数组，按类型选编码：
   - 整数与时间：delta、delta-of-delta、simple-8b、run-length；
   - 低基数枚举：字典编码；
   - 浮点：XOR-based；
3. 同时按 `segmentby`（分组列，如 `farm_id`）组织，按 `orderby`（排序列，通常时间）排序；
4. 查询时只解压需要的列（列裁剪），并做向量化扫描。

**为什么比行存省这么多**：

| 来源 | 说明 | 量级 |
|---|---|---|
| 行开销 | 每行的元组头、对齐填充消失 | 每行 20+ 字节 |
| 索引开销 | 列存不需要逐行 B-Tree，`segmentby/orderby` 替代 | 相当于去掉 30–60% 的二级索引体积 |
| 列内相关性 | 同列值相近，delta/XOR 效果好 | 2–10× |
| 类型编码 | 定长 varchar 与 JSON 文本被字典化 | 视基数而定 |

**代价（必须写清）**：
1. 压缩块上的零散 `UPDATE`/`DELETE` 会解压一小段，代价高；
2. 大改数据要先 `convert_to_rowstore` → 改 → 再转回列存；
3. 改表结构要先停压缩策略；
4. **对我们的直接风险**：NWP 的迟到修订若落进已压缩的老 chunk，就走上面第 1、2 条。对策是**压缩年龄阈值 > 最大修订延迟**（起步 90 天），并定期用 `received_at - valid_at` 的分布复核。

### 5.3 连续聚合（continuous aggregate）

**工作机制**：

1. 把一条聚合查询注册成连续聚合（本质上是一个物化视图，但由扩展托管）；
2. 后台按策略增量刷新：只重算被新数据影响的时间桶；
3. 用 watermark 记录“已物化到哪里”，并用失效区间记录“哪些历史桶被迟到数据改过”；
4. 开启“实时聚合”时，查询会把“尚未物化的最近一段原始数据”与“已物化结果”合并返回——看板永远看到最新数据。

**与原生物化视图的差别**：

| 能力 | `REFRESH MATERIALIZED VIEW` | continuous aggregate |
|---|---|---|
| 刷新方式 | 全量重算 | 增量（只算变更桶） |
| 刷新成本 | 随历史线性增长 | 与增量成正比 |
| 锁 | 默认阻塞读（CONCURRENTLY 有额外限制） | 不阻塞 |
| 迟到数据 | 只能整体重刷 | 自动进入失效区间重算 |
| 实时性 | 刷新周期决定 | 可开实时合并 |

**对我们的意义**：误差日报（分站 × 提前量 × 按天）、可用率日报都可以做成连续聚合，看板查询不再扫原始表。

**代价**：连续聚合的查询受限（不能随意用窗口函数、自连接），口径变更要重建视图；刷新窗口没配好会拖住后台作业。

### 5.4 策略与作业（policies / jobs）

三类策略，全部由库内后台 worker 执行：

```sql
SELECT add_columnstore_policy('nwp_revisions', INTERVAL '90 days');      -- 冷数据转列存
SELECT add_retention_policy('nwp_forecasts', INTERVAL '2 years');        -- 到期 DROP CHUNK
SELECT add_continuous_aggregate_policy('cagg_error_daily',
       start_offset => INTERVAL '30 days',
       end_offset   => INTERVAL '1 day',
       schedule_interval => INTERVAL '1 hour');                          -- 增量刷新
```

作业有运行历史：`timescaledb_information.jobs`（定义）与 `job_stats`（上次运行时间、状态、耗时、失败原因）。这比 cron + 脚本强的地方在于：**失败可见、可重试、不会重叠执行**。

**代价**：`DROP CHUNK` 不可撤销，保留策略的年龄要保守；作业本身要监控。

### 5.5 时序函数

| 函数 | 作用 | 我们的用法 |
|---|---|---|
| `time_bucket(interval, ts)` | 按任意粒度分桶 | 小时/日/周聚合 |
| `time_bucket_gapfill(...)` | 生成连续时间轴，缺桶补 NULL | 观测缺测对齐 |
| `locf(value)` | “上一个有效值”填充（只向前） | 缺口填充，方向天然安全 |
| `interpolate(value)` | 线性插值（两侧） | 仅用于展示，不用于特征 |
| `time_weight(...)` + `average()` | 时间加权平均 | 15 分钟升小时，避免简单平均有偏 |
| `percentile_agg` / `uddsketch` | 分位数近似 | 误差分布看板 |

**为什么重要**：在原生 PG 里，这些都要手写窗口函数 + `generate_series` 左连接，长查询难维护，而且很容易把“缺测”和“真 0”混成一件事——对功率数据来说，这是严重的语义错误。

### 5.6 查询侧增强

- **SkipScan**：优化 `SELECT DISTINCT`（如“有哪些 run_id”）。注意 PG 18 本身新增了 B-tree skip scan，这项优势在收窄。
- **chunk skipping**（2.17+）：为非时间列的过滤也跳过整块，需显式开启，适合 `source`、`run_id` 这类稀疏维度。
- **向量化聚合**：列存上按批处理，减少解压与函数调用次数。

### 5.7 运维连续性

| 项 | TimescaleDB 怎么做 |
|---|---|
| 全量备份 | `pg_dump` / `pg_basebackup` 照旧 |
| PITR | WAL 归档照旧 |
| 恢复前后 | `timescaledb_pre_restore()` / `timescaledb_post_restore()` 处理扩展元数据 |
| 流复制 | PG 原生流复制 |
| 逻辑复制 | **不推荐**（需要分区根表 schema 同步） |
| 升级 | 先升扩展，再升 PG 小版本 |

### 5.8 四条硬限制与我们的对应

| 限制（官方） | 我们的情况 | 结论 |
|---|---|---|
| 分区列不能为 NULL | 四张表时间列均 NOT NULL | 满足 |
| 唯一索引必须包含分区列 | 四张表主键都含时间列 | 满足 |
| 不支持把行更新到另一个 chunk | `upsert()` 不改时间列 | 满足（要写进代码注释） |
| hypertable 之间不能建外键 | 外键都指向 `wind_farms` / `model_runs` 普通表 | 满足 |

## 第六章　实测：列存压缩实测收益

### 6.1 为什么需要实测

官方口径是“最高约 90%”，但那是理想数据（低基数指标、强时间相关性）。我们的表里有 `raw_timestamp`（varchar）、`quality`（json）、`availability`（varchar）这类“对列存不友好”的字段，必须自己量。

### 6.2 测量方法

不能直接在 Mac 上装 TimescaleDB（PG 18.7 超出 2.32.0 支持上限），所以用**代理测量**：

1. 用 `COPY ... TO` 把三张表导出为 CSV（含表头，时间列按 ISO 解析）；
2. 用 Polars 读入，推断类型后写成 Parquet，压缩 `zstd` 级别 3；
3. 对比四组数字：PG 堆大小、PG 索引大小、PG 合计、Parquet 体积；
4. 计算相对堆大小的降幅。

**为什么这个代理可信**：Parquet 与 TimescaleDB 列存都做三件事——按列组织、按类型编码（字典/RLE/delta 类）、块级压缩。两者的**量级**会一致；具体倍数会有差异（编码器不同）。

### 6.3 结果

| 表 | 行数 | PG 堆 | PG 索引 | PG 合计 | 列存+压缩 | 相对堆 | 相对合计 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `nwp_forecasts` | 175,440 | 49 MB | 7.4 MB | 56 MB | **4.65 MB** | −90.5% | −91.8% |
| `predictions` | 127,296 | 13 MB | 17 MB | 30 MB | **1.50 MB** | −88.5% | −95.0% |
| `power_observations` | 175,440 | 13 MB | 7.4 MB | 20 MB | **1.42 MB** | −89.1% | −93.0% |

三个读数值得单独说：

1. **预测表的索引（17 MB）大于数据本身（13 MB）**——列存把这块 secondary index 开销直接消掉，所以“相对合计”的降幅（95%）比“相对堆”（88.5%）更接近我们的真实收益。
2. **NWP 表降幅最大（91.8%）**：它的 varchar 字段重复度高，字典编码效果好。
3. **功率表行数相同但体积更小**：字段少、数值连续性强，delta 编码友好。

### 6.4 局限与不确定性

| 局限 | 影响方向 | 说明 |
|---|---|---|
| Parquet ≠ Timescale 编码器 | 双向 | Timescale 对时间列有 delta-of-delta，可能更好；Parquet 的行组划分可能更好 |
| 不含索引重建成本 | 高估收益 | 真机上列存 chunk 仍有一些元数据开销 |
| 不含解压 CPU 成本 | 高估收益 | 查询要付解压代价，换来 I/O 减少 |
| 样本仅 17 万行 | 低估收益 | 大表上列内相关性更强、字典更省 |
| zstd 级别 3 | 低估收益 | 更高级别可再省 10–20%，但解压更慢 |

**结论**：**“约 −90%”这个量级可信**；具体到某张表的倍数，以真机 `hypertable_columnstore_stats` 为准（P0 要做的事）。

### 6.5 换算到生产规模

按 50 站口径（NWP 每年 526 万行、预测 350 万行、观测 175 万行）：

| 数据 | 三年行数 | 行存估算 | 列存估算 | 差额 |
|---|---:|---:|---:|---:|
| NWP | 1,577 万 | 约 5 GB | 约 0.5 GB | −4.5 GB |
| 预测 | 1,051 万 | 约 2.5 GB（含索引 4 GB） | 约 0.4 GB | −3.6 GB |
| 观测 | 526 万 | 约 0.6 GB | 约 0.1 GB | −0.5 GB |

即使不打折，三年数据在单机 200 GB SSD 上都非常宽裕；打上备份与膨胀冗余也够。**收益的主要意义不是“省钱”，而是“不用为了省空间去写归档脚本、不用在删除时担心表膨胀”**。

### 7.2 对我们的实际含义

1. **内部使用没有任何障碍**：自己出预报、自己看板、自己训模型，属于“自建自用”，免费。
2. **不能把数据库能力打包成服务售卖**：若将来交付给客户的平台允许客户直接访问数据库（获取连接并自行执行 SQL），则触及 TSL 许可限制。

4. **法务确认点**（若要做交付平台）：
   - 客户拿到的是 API 还是数据库连接？
   - 是否按“数据库容量/实例”计费？
   - 是否允许客户在实例上自建表与查询？

### 7.3 版本与支持策略

- 社区版（TSL）由 TigerData 维护，release notes 公开，安全修复随版本发布（2.32.0 一次修了较多安全问题，官方建议尽快升级）。
- **没有商业支持合同**时，升级节奏由我们自己定：跟安全公告，季度评估小版本。
- 版本耦合要写进运维手册：**先升 TimescaleDB，再升 PostgreSQL**；每次升级前查 release notes 的兼容矩阵。

## 第八章　生产部署方案

前提：**生产环境部署在 Linux 服务器上**；本地开发机仅用于开发与实验，其数据库不作为迁移对象。

### 8.1 版本矩阵

| 组合 | 状态 | 说明 |
|---|---|---|
| PG **18.6** + TimescaleDB **2.32.0** | ✅ 官方兼容 | **生产选这个** |
| PG 18.7 + 2.32.0 | ❌ 不兼容 | 2.32.0 的支持上限是 18.6 |
| PG 17.11 + 2.32.0 | ✅ 官方兼容 | 保守选择，17 线更成熟 |
| PG 16.15 + 2.32.0 | ✅ 官方兼容 | 仅在已有 16 环境时选 |

**升级铁律**：先升 TimescaleDB，再升 PostgreSQL。发布说明明确写了这一点——反过来会直接启动失败。

**关于 PG 19**：计划 2026-11-19 GA，但首个 GA 版本不上生产，等 19.1 修复版再评估；即便到那时，也要先确认扩展支持 19。

### 8.2 部署形态

#### A. 单机（开发 / 预发）

```
┌──────────────────────────────┐
│ Linux 主机                    │
│  └─ docker: timescaledb-ha:pg18 │
│       └─ 数据卷（持久化）      │
└──────────────────────────────┘
```

- 官方生产级镜像 `timescale/timescaledb-ha:pg18`，含常用扩展；
- 端口只对内网开放；
- 用途：迁移演练、验收、演示；不承接生产流量。

#### B. 主备 + 自动切换（生产推荐起步）

```
        ┌────────────┐        ┌────────────┐
应用 ──▶│ PgBouncer  │───────▶│   主库     │
        └────────────┘        │  PG 18.6   │
                              │  + TS 2.32 │
                              └─────┬──────┘
                                    │ 流复制
                              ┌─────▼──────┐
                              │   备库     │◀── 报表/分析（只读）
                              └─────┬──────┘
                                    │
                    ┌───────────────┴───────────────┐
                    │  WAL 归档（对象存储）          │
                    │  pgBackRest 每日全量 + 增量     │
                    └───────────────────────────────┘
```

| 项 | 方案 |
|---|---|
| 复制 | PG 原生流复制（异步起步；RPO 要求 0 时改同步） |
| 切换 | Patroni + etcd/Consul，或云托管自动切换 |
| 防脑裂 | fencing（STONITH 或 API 隔离） |
| 备份 | pgBackRest：每日全量 + 持续 WAL 归档，保留 14–30 天 |
| 报表 | 走备库，避免大查询影响写入 |

目标：RPO ≤ 5 分钟（异步）或 0（同步），RTO ≤ 1 分钟（自动切换）。

**起步阶段暂不采用 Kubernetes 的原因**：备份、PVC 扩容、升级编排均比裸机复杂；在团队缺少 K8s 运维经验的前提下，方案 B 运维复杂度更低。

#### C. Kubernetes（已有集群时）

- 可用 CloudNativePG / StackGres / Zalando Postgres Operator / Crunchy PGO，都能跑 TimescaleDB 镜像；
- 需要额外处理：备份与 PITR 的编排、PVC 扩容、升级顺序、节点亲和；
- 适合“公司已经统一在 K8s 上跑服务”的场景。

### 8.3 容量与规格

起步规格：**4 vCPU / 16 GB 内存 / NVMe SSD 200 GB**。

| 场景 | 三年数据量（列存后） | 说明 |
|---|---|---|
| 10 站（现状） | < 1 GB | 现状 115 MB |
| 50 站（含 NWP 4 批/天） | 约 2–4 GB | 见 6.5 换算 |
| 100 站 + 多模型版本 | 约 5–8 GB | 仍在单机范围 |
| 备份（14 天全量 + WAL） | 约 3–5 倍数据库体积 | 存对象存储，不占本地盘 |

扩容信号（出现任一条就该动）：

1. 活跃 chunk 的索引超过内存 25% → 调小 chunk 间隔，或加内存；
2. 查询 P95 连续两周上升 → 先看执行计划与是否缺索引，再考虑扩容；
3. 磁盘使用 > 70% → 先开更早的压缩/保留策略，而不是先买盘；
4. 复制延迟 > 30 秒 → 查网络与 WAL 生成速率。

### 8.5 对象设计

原则：**大表转 hypertable，小表保持普通表**。生产新表的时间列一律 `TIMESTAMPTZ`（官方对时间维度列的首选建议）。

| 表 | 处理 | 分区键 | chunk 间隔 | 说明 |
|---|---|---|---|---|
| `power_observations` | hypertable | `observed_at` | 30 天 | 每站每小时一行，数据量小 |
| `nwp_forecasts` | hypertable | `valid_at` | 7 天 | 查询几乎都带时间窗 |
| `nwp_revisions` | hypertable | `valid_at` | 7 天 | `source` 可做 chunk skipping |
| `predictions` | hypertable | `valid_at` | 7 天 | 按目标时刻查；run 级删除会跨块，通过索引覆盖查询开销 |
| `wind_farms` / `model_runs` / `dataset_splits` | 普通表 | — | — | hypertable 之间不能建外键，必须留一侧 |

**分区策略：只按时间，不加场站哈希维度。** 理由：

- 10–100 个站的站内查询用普通索引 + 裁剪就够；
- 加空间维度会让 chunk 数乘以分区数，元数据与规划开销上升；
- 唯一索引本来就必须含 `farm_id`，加维度不会带来额外收益。

### 8.6 策略配置

```sql
-- 冷数据转列存（阈值 > 最大修订延迟）
ALTER TABLE nwp_revisions SET (timescaledb.compress = true);
SELECT add_columnstore_policy('nwp_revisions', INTERVAL '90 days');
ALTER TABLE nwp_forecasts SET (timescaledb.compress = true);
SELECT add_columnstore_policy('nwp_forecasts', INTERVAL '180 days');
ALTER TABLE predictions SET (timescaledb.compress = true);
SELECT add_columnstore_policy('predictions', INTERVAL '180 days');

-- 保留策略（先注释，确认留存年限再开；DROP CHUNK 不可撤销）
-- SELECT add_retention_policy('nwp_forecasts', INTERVAL '2 years');
-- SELECT add_retention_policy('predictions',   INTERVAL '3 years');
-- SELECT add_retention_policy('power_observations', INTERVAL '5 years');

-- 连续聚合：误差日报
CREATE MATERIALIZED VIEW IF NOT EXISTS cagg_error_daily
WITH (timescaledb.continuous) AS
SELECT time_bucket(INTERVAL '1 day', valid_at) AS bucket,
       run_id, lead,
       count(*) AS n,
       avg(prediction - actual) AS bias,
       avg((prediction - actual) ^ 2) AS mse
  FROM predictions
 WHERE actual IS NOT NULL
 GROUP BY 1, 2, 3
WITH NO DATA;

SELECT add_continuous_aggregate_policy('cagg_error_daily',
       start_offset => INTERVAL '30 days',
       end_offset   => INTERVAL '1 day',
       schedule_interval => INTERVAL '1 hour');
```

阈值怎么定：

| 策略 | 起步值 | 依据 |
|---|---|---|
| NWP/预测压缩 | 180 天 | 迟到修订集中在几天内，180 天足够安全 |
| 修订表压缩 | 90 天 | 修订表本身就是“迟到数据”，阈值要更大 |
| 功率观测压缩 | 暂不开启 | 年增量小（约 175 万行/50 站），保留行存即可 |
| NWP 保留 | 2 年 | 回测与复盘需求 |
| 预测保留 | 3 年 | 考核与追溯 |
| 观测保留 | 5 年 | 长期分析 |

### 8.7 迁移步骤

从现有 PostgreSQL 迁到 TimescaleDB 实例，顺序不可乱：

| 步 | 动作 | 关键点 |
|---|---|---|
| 1 | **冷备**：`pg_dump -Fc` 全量 | 唯一可靠的退路，不是可选项 |
| 2 | 起新实例：PG 18.6 + TimescaleDB 2.32 | 先 `CREATE EXTENSION` |
| 3 | Alembic 迁到最新（不含 hypertable 语句） | 结构先对齐 |
| 4 | 灌数据：先普通表，后大表 | 大表灌完再转超表最快 |
| 5 | `create_hypertable(..., migrate_data => true)` | 比“先建超表再逐行灌”快一个量级 |
| 6 | 校验：行数、求和、场站数、时间范围、抽样 | 四项逐表比对 |
| 7 | 切应用：改 `DATABASE_URL`，先只读验证再切写 | 观察一周作业与压缩率 |

**校验 SQL**（每表四项）：

```sql
SELECT count(*), round(sum(power)::numeric, 6), min(observed_at), max(observed_at)
  FROM power_observations;
```

**回滚**：TimescaleDB 没有官方“撤销 hypertable”路径，只能靠第 1 步恢复或切回旧实例。**逻辑复制不可用**（官方不推荐同步超表），所以不存在“边同步边切”的平滑方案；必须接受一次短暂停机（我们数据量小，10 分钟级）。

### 8.8 备份与 PITR

| 项 | 方案 |
|---|---|
| 工具 | pgBackRest（推荐）或 pg_basebackup + WAL 归档 |
| 全量 | 每日一次，保留 14 天 |
| 增量 | 持续 WAL 归档，保留 30 天 |
| 存储 | 对象存储（S3 兼容），与数据库不同故障域 |
| 校验 | 备份后 `pgbackrest info` 检查；每季度做一次“恢复到临时实例 + 跑验收 SQL” |
| 演练 | **每月一次**恢复演练，记录实际耗时（否则备份等于没有） |

恢复顺序：恢复基础备份 → 回放 WAL 到目标时间点 → `timescaledb_pre_restore()` → 恢复数据 → `timescaledb_post_restore()`。

### 8.9 高可用

| 项 | 做法 |
|---|---|
| 复制 | 流复制（异步起步；RPO=0 时同步） |
| 自动切换 | Patroni + etcd/Consul；或云托管 |
| 防脑裂 | fencing：STONITH、云 API 隔离、或仲裁 |
| 应用连接 | 指向 VIP/代理；重试带退避；区分读写与只读连接串 |
| 只读流量 | 报表、导出走备库 |
| 故障演练 | 每季度做一次主库 kill -9 的切换演练 |

|---|---|---|
| 后台作业失败 | `timescaledb_information.job_stats` | 任一 `last_run_status <> 'Success'` 立即告警 |

### 8.11 安全

| 项 | 做法 |
|---|---|
| 角色分离 | `app_rw`（无 DDL）、`app_ro`（只读，给报表）、`migrator`（仅发布时用） |
| 认证 | `scram-sha-256` + TLS |

### 8.12 上线检查清单

1. 安装指定小版本，`initdb --encoding=UTF8 --locale=C`；
2. 写入 8.4 参数并重启，`SHOW` 逐项核对；
3. 建角色、库，配置 `pg_hba` 与 TLS；
4. `CREATE EXTENSION timescaledb`，再 `alembic upgrade head`；
5. 转 hypertable，导入历史，跑验收 SQL（行数、时间范围、约束违规为 0）；
6. 配置 WAL 归档，做一次 PITR 演练并记录耗时；
7. 接监控告警，跑一次慢查询基线；
8. 用真实起点做端到端预测，核对幂等（重复运行行数不变）。

### 8.13 与本项目代码的衔接

| 事项 | 现状 | 需要做什么 |
|---|---|---|
| `health()` 版本检查 | 硬编码要求 `18.6`，运行是 `18.7` 会直接报错 | 改成“主版本 18，允许小版本差异” |

| 预测输入追溯 | `predictions` 未记录数据批次 | 增加批次/快照标识 |

## 第九章　与纯 PostgreSQL 分区方案的关键差异澄清

针对“仅使用原生 PostgreSQL 声明式分区作为主库、待数据达到亿级后再引入 TimescaleDB”的常见替代方案，本节重点澄清其与本报告方案的三项关键技术差异，并汇总工程细节建议。

### 9.1 可复用的通用工程实践

以下原生 PostgreSQL 最佳实践已直接纳入第八章生产部署设计：

1. 时间列统一使用 `TIMESTAMPTZ`（见 8.5 节）；
2. 入库时间列建立 BRIN 索引（见 8.4 节）；
3. 高频 `UPSERT` 表设置 `fillfactor=90` 与较激进的 autovacuum 阈值（见 8.4 节）；
4. 模型权重存储于文件系统并记录 SHA-256 校验值，数据库仅存路径。

### 9.2 关键差异一：增长最快的大表是 NWP，而非功率观测

在评估是否需要早期引入时序能力时，常误以为“场站级功率观测年增量仅百万行级”即可推迟考虑：

| 数据口径 | 估算公式 | 每年增量行数 |
|---|---|---:|
| 场站级功率观测（15 分钟） | 50 × 96 × 365 | **175 万**（百万级） |
| 机组级遥测（2000 台 × 96 点，对照域） | 2000 × 96 × 365 | 7,000 万 |
| **NWP 预报（50 站 × 4 批 × 72 提前量）** | 50 × 4 × 72 × 365 | **526 万** |

风电功率预测主链路中，**行数增长最快、体积最大的是 NWP 预报（功率观测的 3 倍），其次是预测明细**。以功率观测的增量低估整体时序表规模，容易误判压缩与分区管理的触发时机。

### 9.3 关键差异二：原生声明式分区无法平滑升级为 hypertable

若早期对时序大表采用 PostgreSQL 原生 `PARTITION BY RANGE` 按月分区，后续仍无法通过直接执行 `CREATE EXTENSION` 实现平滑升级。TimescaleDB 官方 `create_hypertable()` 文档明确限制：

> You cannot run `create_hypertable()` on a table that is already partitioned using declarative partitioning or inheritance.

这意味着一旦按原生声明式分区建表并积累历史数据，日后切换至 TimescaleDB 必须经历拆分区、重建表与全量重灌数据；叠加官方不推荐对超表使用逻辑复制且 hypertable 无直接撤销路径，“先原生分区、以后再挂载”本质上是一次停机数据迁移，而非在线扩展挂载。

### 9.4 关键差异三：TimescaleDB 是 PostgreSQL 扩展，而非独立时序库

将 TimescaleDB 与 InfluxDB、ClickHouse 等独立系统归为一类，容易得出“等规模大再切换”的推论。但实际上 TimescaleDB 运行在 PostgreSQL 内核之上，事务、外键、JSONB、备份、高可用与 ORM 均完整沿用。与纯 PostgreSQL 方案相比，真实权衡仅在于**小版本耦合**与 **TSL 许可证边界**，而不存在“时序能力 vs 关系完整性”的二选一取舍。

### 9.5 设计细节对比与建议

| 常见设计写法 | 潜在问题 | 推荐方案 |
|---|---|---|
| `wind_dir_100m` 存储 0~360° 角度 | 角度在 0°/360° 处存在数值跳变，影响统计与建模 | 存储 `u100`/`v100` 分量，或 sin/cos 编码 |
| `air_density` 作为独立物理字段 | 属于派生量，易与温度/气压字段产生口径不一致 | 使用 `GENERATED ALWAYS AS` 生成列 |
| `COPY ... TO PROGRAM` 导出 Parquet | 依赖服务端 shell，权限面较大且异常排查困难 | 使用 `COPY TO STDOUT` 交由导出程序，或通过 DuckDB 只读扫描 |
| 月分区 + 手写冷热归档脚本 | 需额外维护脚本调度、监控与失败重试 | 使用 `add_columnstore_policy` + `add_retention_policy` |

## 第十章　结论、风险与启动条件

### 10.1 选型决策摘要

| 决策项 | 结论 | 核心依据 |
|---|---|---|
| **生产主库** | **PostgreSQL 18.6 + TimescaleDB 2.32.x** | 生产口径评分 93.6 vs 83.2；列存代理实测压缩约 −90%；沿用完整关系生态 |
| **部署环境** | Linux 服务器主备架构（见第八章） | 满足生产环境多进程并发、流复制、PITR 与高可用要求 |
| **本地开发库** | 保持本机 PostgreSQL 18.7，不迁移 | 本地库仅用于离线实验与开发调试，数据规模小（约 115 MB） |
| **当前执行策略** | **备而不发**：迁移草案写好但不执行 | 待真实数据接入且满足 10.3 启动条件时再执行迁移，避免无效运维 |

### 10.2 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 扩展与 PG 小版本耦合 | 升级顺序错会直接失败 | 版本矩阵写进运维手册；升级前查 release notes |
| 压缩块被迟到修订改写 | 写放大、作业变慢 | 压缩阈值 > 最大修订延迟；定期复核 `received_at - valid_at` |
| TSL 许可边界 | 做交付平台时可能触及授权限制 | 应用与库分离交付；法务确认三个问题 |
| 迁移不可逆 | 回滚只能靠备份 | 迁移前冷备；恢复演练 |
| 观测缺测与限电 | 特征与标签失真（比选型更影响精度） | 接入 `is_curtailed`、`received_at`、质量标记 |
| 备份未演练 | 故障发生时无法有效恢复 | 每月恢复演练，记录 RTO |
| 版本漂移（代码要求 18.6、运行 18.7） | 健康检查误报 | 改 `health()` 为“主版本 18”语义 |

### 10.3 启动条件（满足任一项即触发执行）

1. 真实数据接入后日均新增 > 10 万行，或任一表 > 5,000 万行；
2. 需要看板类聚合查询（分站 × 提前量 × 按周的误差、可用率）；
3. 需要按年限自动清理历史数据。

### 10.4 分阶段计划

| 阶段 | 内容 | 交付物 |
|---|---|---|
| P0 | 真机验证：迁移耗时、实际压缩率、5 条典型查询 P50/P95 | 一份实测数字对照表 |
| P1 | 草案转 Alembic 幂等迁移 | `0003_timescaledb` + 演练记录 |
| P2 | 开列存/保留策略，接两张连续聚合 | 策略配置 + 一周作业历史 |
| P3 | 用 `pg_dump` 恢复一次，确认 RTO | 恢复演练报告 |

| 术语 | 含义 |
|---|---|
| hypertable | 按时间自动分区的超表，逻辑上是一张表 |
| chunk | 超表的物理分区，覆盖一个时间区间 |
| hypercore | 行存 + 列存的混合存储；冷 chunk 转列存 |
| segmentby | 列存的分组列（如 `farm_id`），决定压缩单元 |
| orderby | 列存的排序列（通常时间） |
| continuous aggregate | 增量刷新的物化视图 |
| watermark | 连续聚合“已物化到哪里”的标记 |
| BRIN | 块级范围索引，适合单调递增列 |
| MVCC | 多版本并发控制，读写不阻塞 |
| WAL | 预写日志，崩溃恢复与复制的基础 |
| PITR | 时间点恢复（基于全量 + WAL 回放） |
| RPO / RTO | 能容忍丢多少数据 / 多久恢复 |
| TSL | Timescale License，Community 版许可 |
| origin | 预测起点（一次预测覆盖 24 小时的起始时刻） |
